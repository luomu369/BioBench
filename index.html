摘要

在计算生物学和 AI 制药领域，结构预测、分子生成、蛋白/多肽设计、分子对接、分子动力学以及 ADMET 评价已经形成丰富的算法与工具生态，但“工具很多”并不等于“科研流程已经自动化”。真实研究任务需要在不同程序、数据格式和计算环境之间反复切换。

BioBench 的目标，是把这些分散的生物计算能力重新组织成 Agent 可以理解、调用、组合和执行的 Skills。项目以 Agent 为任务入口，以 Skills 为能力单元，以 DGX Spark 的本地 AI 与计算资源为执行基础，以 Web Viewer 为结果呈现界面，形成“自然语言提出任务—Agent 拆解任务—Skill 执行计算—结果回到可视化工作台”的闭环。

一、我们真正想做的，不是再造一个工具

2026 年 9 月 21 日，我们开始进入 DGX Spark Agent Skills 开发挑战赛的实际开发阶段。最初提出了 AI 自动化设计和优化环肽药物、自动化视频生产两个方向，经过讨论最终确定“BioBench：一个生物工作台”。

我们的宏观叙事：把 AI 从“会回答问题”推进到“能够完成科研工作流”。

最终产品不是十几个按钮的工具集合，而是一个面向生物分子设计与分析的智能工作台。中央区域呈现蛋白质、配体和复合物三维结构；左侧提供结构指标、链信息和序列；右侧保留 Agent 对话区，使任务提出、计算过程和结果观察处于同一个界面。

二、核心架构：Agent → Skill → Scientific Engine → Viewer

用户提出任务后，Agent 理解并拆解任务，根 SKILL 负责路由与编排，Deploy Skill 准备环境，Run Skill 执行科学计算，结果写入统一工作区，Viewer 负责呈现。

User ↓ Agent / Harness ↓ BioBench 根 SKILL.md ├─ 任务理解 / 路由 / 编排 ├─ Deploy Skills：环境、模型、依赖、GPU、权重 └─ Run Skills ├─ 结构预测 ├─ 口袋检测 ├─ 分子生成 / 编辑 ├─ 蛋白 / 结合肽设计 ├─ 分子对接 ├─ 分子动力学 ├─ 序列设计 / 搜索 ├─ 结构比较 └─ ADMET 预测 ↓ Scientific Models / Tools ↓ Result Artifacts ↓ BioBench Viewer

这种设计避免 Agent 直接凭记忆操作复杂科研软件，而是通过结构化、可复用、可验证的 Skills 完成专业工作。

Deploy Skills解决模型权重、Python、CUDA/PyTorch 和系统依赖的准备；Run Skills执行真正的科研动作；_shared统一路径、结构文件、环境匹配和错误处理；Viewer把计算结果重新变成蛋白结构、序列、指标等科研对象。

四、开发流程：从一个想法到一个可以运行的工作台

为了在有限的开发周期内把“Agent 能做生物计算”真正落到可运行的系统上，我们没有从一个完整的大模型应用开始，而是采用“先拆能力、再接计算、再做编排、最后形成工作台”的方式推进。整个开发过程可以概括为一个约十日的迭代闭环：需求定义 → 架构设计 → Skill 拆分 → 科学引擎接入 → Agent 编排 → Viewer 开发 → 联调测试 → 部署与演示。

Day 1–2 需求与架构设计 ↓ 明确“让 Agent 执行生物计算”的目标 梳理典型科研任务与输入 / 输出 确定 Agent → Skill → Scientific Engine → Viewer 架构 Day 2–3 Skill 体系拆分 ↓ 将科研能力拆成可独立调用的 Skill 建立 Deploy / Run / Shared / Viewer 分层 统一 Skill 的触发条件、输入、输出和执行方式 Day 3–5 科学能力与运行环境接入 ↓ 准备模型、权重、Python / CUDA / PyTorch 等依赖 接入结构预测、口袋检测、分子生成 / 编辑、 蛋白 / 结合肽设计、分子对接、分子动力学、ADMET 等能力 让每个 Skill 能够独立完成一次可验证计算 Day 5–6 Agent 路由与任务编排 ↓ 建立根 SKILL.md 作为能力入口 Agent 根据自然语言任务识别所需 Skill 将多个 Skill 按任务依赖关系串联起来 Day 6–8 Viewer 与结果层开发 ↓ 统一结构文件、序列、链信息、状态和指标 将计算结果回写到工作区 在 Web Viewer 中展示三维结构与关键结果 Day 8–9 全链路联调 ↓ 测试“自然语言 → Agent → Skill → 科学计算 → Result → Viewer” 检查环境、路径、参数、文件格式和失败情况 修正 Skill 之间的衔接问题 Day 9–10 Demo 打磨与项目交付 ↓ 整理 README / Skill 文档 / 项目结构 完善部署说明与技术栈说明 准备典型科研任务演示与项目展示视频

第一阶段：明确问题。我们首先把问题从“做一个生物工具”重新定义为“让 Agent 能够调用并组合生物计算能力”。因此，开发重点不再是堆叠功能按钮，而是确定哪些科研动作应该被封装成 Skill，以及这些 Skill 如何被 Agent 理解和调用。

第二阶段：建立 Skill 体系。在确定总体架构后，我们把系统拆成 Deploy、Run、Shared 和 Viewer 四个层次。Deploy Skill 负责环境、模型权重和依赖准备；Run Skill 负责真正的科学计算；Shared 层负责路径、数据格式和通用逻辑；Viewer 则负责把计算结果重新组织成研究者能够观察和理解的科研对象。

第三阶段：接入科学计算能力。我们围绕真实计算生物学工作流逐步接入结构预测、口袋检测、分子生成与编辑、蛋白/结合肽设计、分子对接、分子动力学、序列设计与搜索、结构比较以及 ADMET 预测等能力。这里的关键不是简单调用现有模型，而是把“模型 + 参数 + 环境 + 输入输出约定”一起封装，使 Agent 面对的是稳定的能力接口。

第四阶段：打通 Agent 编排。当单个 Skill 可以独立运行后，我们进一步建立根 SKILL.md 作为统一入口，让 Agent 根据自然语言理解任务并选择相应能力。例如，一个从目标蛋白出发的设计任务，可以依次触发结构准备、口袋分析、候选生成、分子编辑、对接、动力学和 ADMET 等步骤，而不是要求用户手动打开多个程序逐个操作。

第五阶段：建立统一结果层与 Viewer。多种科学计算会产生不同类型的结构文件、序列、状态信息和评价指标，因此我们进一步统一结果的组织方式，并将这些结果回到 Web Viewer 中展示。这样，Agent 的执行过程不再停留在命令行日志，而能够重新映射到蛋白结构、链、序列和计算指标等科研对象上。

第六阶段：全链路测试与交付。最后，我们围绕完整链路进行联调，重点检查 Skill 路由是否正确、依赖环境是否完整、输入输出文件是否匹配、计算失败时是否能够定位问题，以及多个 Skill 连续执行时结果是否能够正确传递。完成验证后，再整理 README、Skill 文档、部署说明和演示流程，形成可以提交、展示和继续扩展的完整项目。

一个典型的 BioBench 工作流可以是：目标蛋白 → 结构预测/加载 → 口袋检测 → 分子或结合肽生成 → 分子编辑 → 分子对接 → 分子动力学 → ADMET。单个 Skill 是一个能力单元，而多个 Skill 按科研逻辑组合后，才形成完整的 Agent 科研工作流。

五、我们的创新：不是增加一个模型，而是改变模型使用工具的方式

  • 从工具集合变成能力网络：重点不是工具数量，而是能否被 Agent 组合。
  • 从“给答案”变成“执行任务”：Agent 可以把对接、动力学、生成等能力作为可执行 Skill。
  • 从单点算法变成科研工作流：多个计算阶段能够连续衔接。
  • 从命令行结果变成可视化科研对象：结果回到蛋白结构、序列、链和指标上下文。
  • 从一次性 Demo 变成可扩展框架：新增模型时可以优先增加 Deploy/Run Skill，而不必重做整个 Agent。
我们对 Agent Skills 的理解：不是给 Agent 增加一个“生物学知识库”，而是给 Agent 增加一套“做生物计算的手”。

六、为什么是 DGX Spark，以及下一步

BioBench 不能只停留在文本层。真实生物计算需要模型推理、结构计算、GPU 加速和大量中间结果处理。DGX Spark 作为本地 AI 与计算底座，使 Agent 更接近实际科学计算执行过程。

下一步，我们将继续提升复杂多步骤任务的自动规划、计算失败后的自动恢复、实验记录与结果追踪、多目标候选筛选，以及蛋白质工程、酶分子设计和 AI 制药模型的覆盖。

结语

传统计算生物学软件给研究者提供一把把工具；BioBench 想做的是把这些工具组织成一个真正能够工作的智能工作台。研究者先描述自己想解决的科学问题，Agent 再把科学问题拆解成可以执行的计算任务，并把每一步结果重新带回科研对象本身。

这就是我们对 Agent Skills 最直接的理解：让 Agent 不只是知道科学，更能够真正参与科学计算。
