摘要

在计算生物学和 AI 制药领域，结构预测、分子生成、蛋白/多肽设计、分子对接、分子动力学以及 ADMET 评价已经形成丰富的算法与工具生态，但“工具很多”并不等于“科研流程已经自动化”。真实研究任务需要在不同程序、数据格式和计算环境之间反复切换。

BioBench 的目标，是把这些分散的生物计算能力重新组织成 Agent 可以理解、调用、组合和执行的 Skills。项目以 Agent 为任务入口，以 Skills 为能力单元，以 DGX Spark 的本地 AI 与计算资源为执行基础，以 Web Viewer 为结果呈现界面，形成“自然语言提出任务—Agent 拆解任务—Skill 执行计算—结果回到可视化工作台”的闭环。

一、项目定位

2026 年 9 月 21 日，我们开始进入 DGX Spark Agent Skills 开发挑战赛的实际开发阶段。最初提出了 AI 自动化设计和优化环肽药物、自动化视频生产两个方向，经过讨论最终确定“BioBench：一个生物工作台”。

我们的宏观叙事：把 AI 从“会回答问题”推进到“能够完成科研工作流”。

最终产品不是十几个按钮的工具集合，而是一个面向生物分子设计与分析的智能工作台。中央区域呈现蛋白质、配体和复合物三维结构；左侧提供结构指标、链信息和序列；右侧保留 Agent 对话区，使任务提出、计算过程和结果观察处于同一个界面。

二、系统架构

用户提出任务后，Agent 理解并拆解任务，根 SKILL 负责路由与编排，Deploy Skill 准备环境，Run Skill 执行科学计算，结果写入统一工作区，Viewer 负责呈现。

User ↓ Agent / Harness ↓ BioBench 根 SKILL.md ├─ 任务理解 / 路由 / 编排 ├─ Deploy Skills：环境、模型、依赖、GPU、权重 └─ Run Skills ├─ 结构预测 ├─ 口袋检测 ├─ 分子生成 / 编辑 ├─ 蛋白 / 结合肽设计 ├─ 分子对接 ├─ 分子动力学 ├─ 序列设计 / 搜索 ├─ 结构比较 └─ ADMET 预测 ↓ Scientific Models / Tools ↓ Result Artifacts ↓ BioBench Viewer

这种设计避免 Agent 直接凭记忆操作复杂科研软件，而是通过结构化、可复用、可验证的 Skills 完成专业工作。

三、Skill 代码结构

Deploy Skills解决模型权重、Python、CUDA/PyTorch 和系统依赖的准备；Run Skills执行真正的科研动作；_shared统一路径、结构文件、环境匹配和错误处理；Viewer把计算结果重新变成蛋白结构、序列、指标等科研对象。

四、十日开发历程

第一天：先看比赛，再想我们能做什么。

9 月 21 日上午 11 点半，林和沙两个人坐在会议室里，把前一天的线上培训回放从头看了一遍。前一天两个人都参加了户外实践活动，所以没能准时参加培训，只能在第二天补上。看完培训之后，我们没有马上开始写代码，而是先讨论了一个很实际的问题：我们自己的专业背景，能和 DGX Spark 以及 Agent Skills 结合起来做什么？

先简单介绍一下两个人。林是北京化工大学的硕士三年级，专业方向是 AI 制药，目前主要做 AI 设计环肽药物；沙是北京化工大学的硕士一年级，主要做计算机辅助酶优化。两个人平时做的东西虽然不完全一样，但都和计算、生物分子以及 AI 有一定交集。所以看完培训后，我们很自然地把思路往自己的专业上靠。

当天我们先提出了两个比较具体的方向：一个是 AI 自动化设计、优化环肽药物，另一个是自动化视频生产。前者是因为和我们的研究方向比较接近，也确实有实际科研场景；后者则是当时觉得 Agent 和生成式 AI 在内容生产上的能力也值得试一试。我们当时主要考虑两件事：一是能不能真正发挥 DGX Spark 的计算能力和大内存优势，二是这个方向做出来之后有没有自己的特点。

不过很快，我们又遇到了一个需要想清楚的问题：DGX Spark 到底应该承担什么角色？是把大模型也部署到本地，让 Spark 更多承担模型推理；还是使用云端大模型，把本地机器主要用于具体的生物计算任务？这个问题当时没有马上得到答案，我们一边看资料，一边继续讨论。

最后，我们没有继续沿着单一的环肽设计或者视频生产往下做，而是把自己的专业背景和比赛的 Agent Skills 方向结合起来，确定了 BioBench——一个面向生物计算的工作台。这个决定基本定下了后面十天的方向：不再单独做某一个模型，而是想办法把我们平时会用到的一些生物计算能力组织起来，让 Agent 能够调用它们。

第二、三天：把想法拆开。方向确定以后，我们开始把 BioBench 到底要做哪些事情一项项列出来。结构预测、口袋检测、分子生成、分子编辑、蛋白/结合肽设计、分子对接、分子动力学和 ADMET 等能力逐渐进入清单。与此同时，我们也开始考虑一个问题：这些功能以后怎么让 Agent 调用？最后逐渐形成了 Deploy、Run、Shared 和 Viewer 的基本分层。

第四、五天：开始真正接模型。这几天主要是在处理运行环境、模型权重、依赖和各种输入输出格式。真正开始跑以后才发现，不同工具之间的差别比想象中大。很多时间并不是花在模型本身，而是花在环境配置、路径、参数和文件格式这些细节上。哪个地方报错，就先把哪个地方解决掉，再继续往下接。

第六天：让 Agent 真正参与进来。前面各个 Skill 能够单独运行以后，我们开始建立根 SKILL.md，尝试让 Agent 根据用户的描述选择合适的 Skill。这个阶段最重要的测试不是“某一个模型能不能跑”，而是多个 Skill 连起来以后，前一步的结果能不能顺利交给下一步。

第七、八天：把结果放到一个地方看。最开始很多结果都散落在终端和不同的输出文件里，自己找起来比较麻烦。所以我们开始做 Viewer，把结构、序列、链信息和一些计算指标整理到统一界面里。这个阶段也反复改了几次，因为不同工具产生的结果并不完全一样。

第九天：开始跑完整流程。前面测试的大多是单个功能，这一天开始把它们真正串起来。从自然语言任务开始，到 Agent 选择 Skill，再到科学计算，最后把结果交给 Viewer。完整跑下来以后，一些单独测试时没有暴露的问题才出现，比如路径不一致、输入文件格式对不上、前后两个 Skill 的参数衔接不上等。

第十天：收尾和重新跑一遍。最后一天主要整理 README、Skill 文档、部署说明和演示流程，同时把几个比较典型的任务重新从头跑一遍。十天时间并不长，很多东西也还没有做到最终形态，但至少我们把最开始的想法变成了一个可以实际运行和继续往下做的项目。

回头看，这十天的开发过程其实没有特别复杂的“秘诀”，更多就是不断试、不断改：先把想法做出来，跑起来以后发现问题，再回头调整 Skill、环境或者流程。BioBench 最终形成的样子，也是在这样的反复过程中慢慢确定下来的。

五、核心创新

  • 从工具集合变成能力网络：重点不是工具数量，而是能否被 Agent 组合。
  • 从“给答案”变成“执行任务”：Agent 可以把对接、动力学、生成等能力作为可执行 Skill。
  • 从单点算法变成科研工作流：多个计算阶段能够连续衔接。
  • 从命令行结果变成可视化科研对象：结果回到蛋白结构、序列、链和指标上下文。
  • 从一次性 Demo 变成可扩展框架：新增模型时可以优先增加 Deploy/Run Skill，而不必重做整个 Agent。
我们对 Agent Skills 的理解：不是给 Agent 增加一个“生物学知识库”，而是给 Agent 增加一套“做生物计算的手”。

六、算力与展望

BioBench 不能只停留在文本层。真实生物计算需要模型推理、结构计算、GPU 加速和大量中间结果处理。DGX Spark 作为本地 AI 与计算底座，使 Agent 更接近实际科学计算执行过程。

下一步，我们将继续提升复杂多步骤任务的自动规划、计算失败后的自动恢复、实验记录与结果追踪、多目标候选筛选，以及蛋白质工程、酶分子设计和 AI 制药模型的覆盖。

结语

传统计算生物学软件给研究者提供一把把工具；BioBench 想做的是把这些工具组织成一个真正能够工作的智能工作台。研究者先描述自己想解决的科学问题，Agent 再把科学问题拆解成可以执行的计算任务，并把每一步结果重新带回科研对象本身。

这就是我们对 Agent Skills 最直接的理解：让 Agent 不只是知道科学，更能够真正参与科学计算。
