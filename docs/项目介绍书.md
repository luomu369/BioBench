# BioBench 项目介绍书

> 一台 DGX Spark，一个 Agent，二十三个技能，和一个网页。
> 用自然语言做分子设计。

---

## 一、这是什么

BioBench 是一个**生物分子设计工作台**。它把本地 GPU 上的一批 AI 模型——结构
预测、结合剂设计、分子生成、分子对接、分子动力学——包装成一组 Agent Skills，
让任何一个能读 `SKILL.md` 并执行 shell 命令的大模型 harness 来驱动它们。

你对它说"在这个口袋设计一个 12 氨基酸的环肽"，它就去跑 BoltzGen；你说"把选中
的那个氢换成苯环"，它就去改结构；你说"做一下动力学模拟看这个姿态稳不稳"，
它就去跑 OpenMM。每一步的结果都发布到同一个网页查看器里，你看着结构一步步
长出来。

它不是又一个 Web UI 包一层 API。**查看器里没有 LLM，也没有后端逻辑**——它是
一个静态页面，渲染技能发布到磁盘上的文件。Agent 在命令行里工作，查看器只负责
显示。这个划分是整件事能跑起来的原因。

---

## 二、为什么是现在

### 2.1 模型已经到位，接口没有

2024 年以来，生物分子领域的开源模型密集出现且质量可用：

| 模型 | 做什么 | 权重大小 |
|------|--------|----------|
| BoltzGen | 结合剂/配体设计（扩散 + 结构预测） | ~10 GB |
| ProteinMPNN | 固定骨架的序列设计 | ~0.5 GB |
| GenMol | 小分子生成（全新/补全/连接） | ~2 GB |
| ResGen | 口袋条件的分子生成 | ~1 GB |
| AutoDock Vina | 分子对接与打分 | 二进制 |
| OpenMM | 分子动力学 | 库 |
| Foldseek / MMseqs2 | 结构与序列搜索 | 二进制 |

这些模型**单个都能用，合起来用不了**。每一个都有自己的 conda 环境、权重下载
方式、输入格式、输出解析。一个课题想走完"找口袋 → 生成分子 → 对接 → 动力学验
证"这条链，要在四套环境、五种文件格式之间手动搬运，每一步都要写胶水代码。

### 2.2 硬件门槛降到了一台机器

DGX Spark（GB10）有 121 GB 统一内存和一块能跑的 GPU。这恰好是 BoltzGen 一次
典型设计所需（约 40 GB）的三倍。**过去需要集群的工作，现在一台桌面盒子就能
做。**

但"能跑"和"能用"之间还有距离：模型在机器上，人却要通过 SSH、conda activate、
python script.py --arg... 来跟它说话。

### 2.3 Agent 改变了交互的单位

大模型 harness 的出现让"用自然语言驱动命令行"成为现实。Agent Skills 规范
（`SKILL.md` + 脚本）给了它一个标准形态：**把领域知识写成文档，把操作写成脚
本，Agent 读文档、跑脚本。**

BioBench 就是把这套形态用在生物分子设计上。它不训练模型，不做推理优化——它
解决的是**编排问题**：让一个通用 Agent 能安全、可复现地驱动这一堆专业工具。

## 三、解决什么问题

### 3.1 核心问题：专业工具的"最后一公里"

一个计算化学工作者面对的真实困难，往往不是"哪个模型更好"，而是：

- **环境**：八个 conda 环境，哪个脚本用哪个 Python？CUDA 版本和 PyTorch
  wheel 怎么匹配？
- **格式**：CIF 转 PDB 时序列号会错位；PDB 是定宽列，一个空格之差就读出错
  的分子；meeko 会静默丢弃它不会模板化的残基。
- **状态**：一个任务跑 50 分钟，中间它在干什么？失败了没有？
- **复现**：上次那个 -5.7 kcal/mol 是用什么参数跑的？

这些问题每一个都不难，但每一个都踩过就会付出一天。BioBench 的做法是：

| 问题 | 解法 |
|------|------|
| 环境 | 每个技能自带 `preflight.py`，跑之前先验证，`--fix` 能修 |
| 格式 | `skills/_shared/pdb_format.py` 统一读写，列宽不合就报错而不是静默错位 |
| 状态 | `publish.py --status` 把进度写到 `status.json`，查看器 2 秒轮询 |
| 复现 | `publish.py --params` 把运行参数写成结构化字段，下次直接读 |

### 3.2 那些"静默失败"

`skills/_shared/silent-failures.md` 记录了一批**不报错但结果错**的坑。这是这个
项目最珍贵的资产，因为每一个都是真实发生过的：

- **`proximityBonding` 把蛋白侧链连到配体上**——它只按距离判断，1.3 Å 的接触
  就是一条键。于是两个分子之间有了一条从未存在过的连接线。
- **蛋白被写成 HETATM**——meeko 的受体制备器按记录类型区分蛋白和配体，
  HETATM 的蛋白残基被静默丢弃，对接分数是在不完整的受体上算的。
- **gemmi 写 PDB 时丢弃序列号**——CIF 里第 11612 号原子，写出来变成了别的原
  子。用户点的那个氢，编辑落在了碳上。
- **一个 12,000 原子的复合物上做 `proximityBonding`**——O(n²) 的邻居网格，
  跑了 21 GB 内存没结束。

这些的共同点是：**文件写出来了，查看器画出来了，看起来对，数字是错的。**
所以 BioBench 的脚本大量使用"拒绝"而不是"猜测"——列宽不合就抛异常，pid 死了
就报告，选中的原子和其他残基重叠就警告。

## 四、架构

### 4.1 三层划分

```
┌─────────────────────────────────────────────┐
│  Agent 层（任意 harness）                     │
│  读 SKILL.md，执行命令，决定做什么             │
└──────────────────┬──────────────────────────┘
                   │ 调用
┌──────────────────▼──────────────────────────┐
│  技能层（skills/，23 个）                     │
│  每个技能 = SKILL.md（知识）+ scripts/（操作） │
│  分三类：部署 / 运行 / 发布                   │
└──────────────────┬──────────────────────────┘
                   │ 读写文件
┌──────────────────▼──────────────────────────┐
│  查看器层（webapp/）                          │
│  静态页面 + 一个薄服务端                       │
│  渲染 current.cif / current.json / status.json│
└─────────────────────────────────────────────┘
```

**层与层之间只通过文件通信。** 没有 RPC，没有消息队列，没有数据库。技能把结
果写到 `webapp/static/` 下的三个文件，查看器每 2 秒轮询一次。

这个选择的代价是轮询有 2 秒延迟。收益是：

- 技能可以用任何语言写，只要会写文件
- 查看器重启不丢状态
- 任何一个技能可以单独测试——跑脚本，看文件
- Agent 可以自己读这些文件来回答"跑到哪了"

### 4.2 发布契约

三个文件构成全部接口：

| 文件 | 内容 | 谁写 |
|------|------|------|
| `current.cif` | 最新结构 | `publish.py --structure` |
| `current.json` | 结构元数据（链、角色、指标、参数、备注） | 同上 |
| `status.json` | 任务列表、当前步骤、进度消息、pid | `publish.py --status` |

`current.json` 里的 `params` 块是后来加的，专门解决"重对接时模型每次都要翻历
史目录"的问题——把盒心、穷举度、配体 SMILES 写成结构化数据，下一次运行直接读。

### 4.3 Agent 面板

查看器右侧是一个聊天面板，背后是 `webapp/agent.py`——一个 opencode 客户端。

```
浏览器                serve.py              agent.py            opencode
  │  POST /agent         │                      │                   │
  ├─────────────────────>│  agent.stream()      │                   │
  │                      ├─────────────────────>│  POST /session/id/prompt_async
  │                      │                      ├──────────────────>│
  │                      │                      │  GET /event (SSE) │
  │                      │                      │<──────────────────┤
  │  SSE: text/reasoning/tool/permission/waiting/done                │
  │<─────────────────────┼──────────────────────┤                   │
```

几个关键设计：

**流式，且只信 opencode 的结束信号。** 一个跑技能的 turn 要几分钟，面板显示
空白会让人以为坏了。所以文本、思考、工具调用都实时转发。而"什么时候算结束"
只用 `session.idle` 和 `message.updated` + `finish`——所有基于超时的规则都试
过，都对一半：短了会在模型还在工作时报告"无回复"，长了让每个简短回答都像卡住。

**权限请求转发给用户。** Agent 要跑白名单外的命令时，opencode 会阻塞等待。
这个请求通过 SSE 转到面板，用户点"允许一次"或"拒绝"。有一个全局开关可以一律
自动批准，代价是 Agent 能不经询问执行任何命令。

**后台任务由面板监控。** 模型提交一个 50 分钟的任务后就结束 turn，但它说"完成
后我会汇报"——这个承诺原来没人守。现在 `stream()` 在结束时检查 `status.json`，
有未完成任务就发 `waiting` 事件；前端每 2 秒轮询 `/agent/jobs`，用 **pid + 进程
启动时间**判断任务是否真的结束（pid 会被系统回收重用，光看 pid 会永远等一个
早就死了的任务）。任务完成后自动发一条唤醒消息，附带日志尾部，模型据此汇报。

**会话永不自动更换。** 曾经 `ensure_session()` 在 session busy 时静默建一个新
的，结果用户在任务运行期间问"还在跑吗"，消息被扔进一个空会话——上下文全丢。
现在 session 的选择权完全在用户：`＋` 新建，`☰` 切换历史，停止按钮中断。

### 4.4 查看器

`webapp/static/index.html`，约 8400 行，3Dmol.js 渲染。左侧三栏（指标、序列、
选择），右侧 Agent 面板，中间是 3D 舞台。

- **多标签**：每个发布的结构一个标签，可切换、可关闭，状态按标签保存
- **选择模式**：残基 / 链 / 原子 / 键 / 口袋，选中内容随问题一起发给 Agent
- **背景可换**：四个预设色 + 自定义图片（canvas 用 alpha 0 透明白，图片在下层）
- **空状态**：一个 logo 加一行介绍

## 五、技能体系

23 个技能分三类：

### 5.1 部署类（8 个）

每个都是"安装 + 验证"：`preflight.py` 检查环境、导入、权重、GPU，能修的加
`--fix`。设计原则是**先验证再跑**——一个缺权重的 BoltzGen 会在跑了 20 分钟
后才失败，而 preflight 在 10 秒内就能说出来。

### 5.2 运行类（13 个）

从找口袋到动力学验证的完整链条：

```
pocket-detection ──> pocket-molecule-design ──> molecular-docking
                         │                            │
                         ▼                            ▼
                    molecule-generation        molecular-dynamics
                         │
                         ▼
                    molecule-editing ──> sequence-design
```

每个运行类技能遵循同一形状：确认参数 → 报告进度 → 执行 → 解释结果 → 发布。

### 5.3 发布类（1 个）

`structure-viewer` 提供 `publish.py`，是所有技能的出口。它做原子写入（先写
`.tmp` 再 rename），记录任务步骤，把 pid 和参数一起存档。

## 六、几个关键决策

### 6.1 为什么用 Agent Skills 而不是写一个 Agent 框架

因为**领域知识比 Agent 循环更难写**。工具调用循环有无数现成实现，但"什么情况
下该用柔性对接"、"meeko 会丢哪些残基"、"这个机器的 CUDA 配哪个 PyTorch
wheel"——这些只能写成文档，而文档需要人来维护。

Agent Skills 规范把这两半分开：`SKILL.md` 是文档，`scripts/` 是操作。Agent 负
责把两者接起来。换一个 harness（Claude Code → Copilot → opencode）不需要重写
任何领域知识。

### 6.2 为什么查看器是静态页面

一开始想加一个后端做实时推送。实际做出来发现：**技能已经在写文件了，查看器只
需要读。** 加一个 WebSocket 服务要多维护一个进程、一个协议、一个失败模式，
而轮询 2 秒的延迟在这个场景里完全够用。

静态页面还带来一个好处：Agent 可以自己读 `status.json` 回答"跑到哪了"，不需
要任何额外接口。

### 6.3 为什么内置 opencode 而不是让用户自己接

试过让用户配 Claude Code 或 Copilot，但每个 harness 的 skill 发现机制、权限
模型、会话存储都不一样。内置一个 opencode（vendored 在 `vendor/bin/`，177 MB）
换来的是：权限系统、会话持久化、上下文压缩、SSE 事件流，全都是现成的。

模型走 StepFun 的 `step-5-preview`（OpenAI 兼容接口），key 存在
`webapp/agent.key`——因为环境变量活不过 VS Code 重启，而查看器比启动它的终端
活得长。

### 6.4 为什么拒绝多于猜测

这个项目里大量的代码是**检查然后退出**：

```python
if value >= 10 ** width:
    raise PdbFormatError(f"{what} {value} does not fit in {width} columns...")
```

```python
if alive is not False:
    return True   # pid 死了就是死了，不猜
```

```python
if others:
    print(f"warning: serial {s} is within 1.6 A of atoms from other residues...")
```

因为生物分子计算的失败大多是静默的——一个错位的序列号、一个被丢弃的残基、一
条虚假的键，都不会报错，只会让数字错。**一个明确的错误消息比一个看似成功的运
行有价值得多。**

## 七、现状与边界

### 7.1 能做什么

- 从 PDB ID 或本地文件加载结构，在网页上查看、选择、测量
- 用自然语言驱动：口袋检测、分子生成、结合剂设计、分子对接、序列设计、
  分子编辑、动力学模拟、结构/序列搜索、ADMET 预测
- 长任务后台运行，面板显示进度，完成后自动汇报
- 多会话管理，历史可切换、可删除
- 权限控制：逐条询问，或一键自动批准

### 7.2 已知的边界

- **opencode 1.18.32 的 bash 工具会卡死**：子进程退出后状态机收不到信号，
  session 永远 busy。目前的解法是停止按钮 abort。
- **`pocket-molecule-design` 会把多个设计叠在一起发布**：10 个分子占同一位置，
  后续编辑会歧义。脚本现在会警告，但发布环节还没修。
- **重对接的亲和力数据曾不可靠**：发布的值和 `summary.json` 不一致，配体也错。
  需要从原始产物重新发布。
- **单用户、单机**：没有多用户，没有远程部署，没有集群调度。

### 7.3 数字

| 项 | 数 |
|---|---|
| 技能 | 23 |
| 技能脚本（Python） | ~7,300 行 |
| 技能文档（Markdown） | ~7,100 行 |
| 查看器 + 服务端 | ~8,400 行 |
| conda 环境 | 8 |
| 外部工具 | 5（vina, foldseek, fpocket, mmseqs, ResGen） |
| 模型权重 | ~14 GB |
